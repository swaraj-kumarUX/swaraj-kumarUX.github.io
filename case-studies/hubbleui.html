HubbleUI design system

PARTICLES looked like a design system. Nothing in production actually used it.

I rebuilt its color foundation from measured, provable drift – then migrated redPro’s first real component onto it, found a shipped accessibility bug on the way, and built the tooling to stop the drift from ever coming back unwatched.

PARTICLES · gray scale audit

Objective

Trust it provably, not just aesthetically. Rebuild PARTICLES’ color foundation into something engineers and designers could actually rely on – then prove it by migrating a real, shipped component onto it.

A token file that’s well-organized on paper but disconnected from production doesn’t help anyone. And a fix that only holds until the next deadline doesn’t either – which is why this work ends in tooling, not just a cleaner file.

The problem

Three compounding issues. PARTICLES existed. It wasn’t trustworthy.

01

The colors drifted

Pasted in over time from different sources rather than engineered. The brand blue wandered between 213° and 223° across its own scale – “blue-100” and “blue-500” weren’t the same blue, just lighter and darker versions of visibly different ones.

02

Accessibility failed

Success, warning and error text – used constantly in a data-dense B2B tool – sat at 3.9–4.3:1 contrast. WCAG AA requires 4.5:1. Real users with low vision couldn’t reliably read status messages.

03

Production wasn’t even connected

Live components – real buttons, badges, inputs on shipped screens – were bound to a third, older system with 151+ legacy variable names. PARTICLES was a well-organized file nothing in production depended on.

Process · 01

Audit before engineering. Rather than guessing at fixes, I audited every family’s hue, saturation and lightness numerically.

Plotting each on a hue wheel makes drift visible instead of eyeballing hex codes. That turns “these colors look a bit off” into a provable finding: blue-800 sits at 2° hue while the rest of the family sits at 8–10° is a fixable fact. “This looks slightly wrong” is not.

Process · 02

Engineer the gray scale from scratch. Grays are the hardest-working color in any interface, and the most tolerant of getting quietly wrong.

12 scattered values became 9 engineered stops: one locked 216° cool undertone to harmonize with the brand blue, and lightness steps that rise unevenly – because human vision compresses differences in dark tones more than light ones. gray-0 stayed deliberately pure white.

Process · 03

Lock hue – without erasing character. Every chromatic family got locked to one mathematically precise hue. But I prototyped a fully “normalized” version too, and rejected it.

The judgment call

Knowing which axis to standardize, and which to leave alone.

The normalized version produced an acidic green, muddy dark ambers, and would have shifted the protected brand blue to a more saturated, less calm color. Hue consistency was worth enforcing everywhere; saturation and lightness needed to stay hand-tuned per family – that’s what reads as designed rather than generated.

Process · 04

Fix accessibility as engineering, not polish. Each failing feedback color needed a specific, calculated darkening – not a guess.

I computed exactly how far each needed to move to clear 4.5:1 against its real background, then applied the minimum change: 2–3% lightness – almost imperceptible, but the difference between passing and failing AA. Each fix folded into the primary token rather than adding parallel “-600” variants.

Process · 05

Migrating Buttons – and finding the real bug. With the foundation solid, I migrated Buttons, the first of 28 components, off the legacy system.

Mapping Buttons’ legacy variables to PARTICLES tokens surfaced a real, shipped accessibility bug: Disabled + Hover rendered white text on a light gray background – essentially invisible.

The symptom

White text on light gray in the Disabled + Hover state – essentially invisible.
→

The defect

Disabled was modeled inside the color-intent axis, beside “Active” and “Destructive” – so it got crossed against every hover and pressed state, combinations that should never have existed.

Symptom vs. defect

Make the bug class impossible, not patched once.

I restructured the variant architecture so Disabled became a state, orthogonal to color intent – matching how Material Design and Adobe Spectrum model it.

The same pass caught that Tertiary was visually almost identical to Secondary. I made it borderless and transparent at rest, giving designers an actual third tier of emphasis.

What I learned

Which inconsistencies were bugs, and which were design decisions dressed up as inconsistencies.

Uniform hue was a bug. Uniform saturation across five different families was not – enforcing it anyway would have made the system worse while looking more “consistent” on paper.

The migration reinforced the same lesson structurally: the visible symptom and the actual defect were two different things. Fixing the axis meant it couldn’t happen again.

Act two · The tool

HubbleUI Design Assistant. A Figma plugin I designed and built myself – ES5 JavaScript in Figma’s sandbox, with its own UI, its own scoring logic, and a direct connection to Claude for the one check that needs a real eye.

Auditing 27 more components by hand doesn’t scale, and neither does trusting every future PR to remember the fixes. Four features, each closing a different way drift actually happens.

01

Audit + auto-fix

Scans fills, strokes, radius, spacing and type against the token scale. Off-system values get a severity, a plain-language reason, and the nearest token – found by colour-distance matching.

02

Adoption Score

One number, five weighted dimensions. Turns “is this on-system?” into something a lead can track over time.

03

Detached Instance Detector

Fully detached layers, broken links to a deleted component, and instances still linked but overridden – each override tagged token-bound or uncontrolled.

04

DAT – AI fidelity check

A developer-build screenshot beside the Figma design; Claude compares colour, type, spacing, components and layout, and returns a scored, structured report.

Systems thinking

Turning “on-system?” into a number. A pass/fail audit tells you what’s wrong on one frame – not whether adoption is improving file over file.

The Adoption Score weights five dimensions by how much each actually signals real adoption, rather than surface compliance.

Component coverage35%

The largest weight – using real components is the strongest signal of adoption.

Token coverage30%

Style checks that resolve to a token.

Detachment, inverse15%

Penalises frames named like a component that aren’t actually linked to one.

Variant configuration10%

Instances with explicit component properties set, not left default.

Naming compliance10%

Smallest on purpose – naming matters for handoff, but it’s cosmetic next to real use.

Drift detection

The drift an audit alone can’t see. An instance still “linked” to CLUSTERS but locally overridden looks compliant in a file search while it’s silently forked from the system.

The Detector separates that from full detachment and broken links, and tags every override as token-bound or uncontrolled – exactly the class of bug that slipped through on Buttons before the migration.

Detached – rebuilt from scratch, no link at all Broken link – the source component is gone Overridden – linked, but a fill swapped or a radius nudged

AI review

Writing the rubric, not just calling the API. A fixed prompt forces structured, comparable output every time – instead of a free-text opinion that reads differently on every run.

Reflection

What I caught in my own tool.

The first Audit only checked whether a value matched a token – a fill that happened to be #315ED1 passed, bound to the brand variable or not. The moment the token changes, an unbound-but-matching value doesn’t follow it, and silently drifts.

Fixing it meant reading Figma’s Variables API properly – getBoundVarName() checks whether a property is genuinely linked to a live variable. The difference between a checker that looks rigorous and one that actually is.

Outcome

A corrected foundation, enforced at the source. The plugin is live and in active use across redPro design work.

Plan – not yet built

Designing with the system, not just checking against it. Give an agent the system itself – tokens, components, rules, patterns – as structured knowledge, so it proposes correct designs instead of getting audited afterward.

01

Knowledge – machine-readable

Tokens follow the same Primitive → Semantic → Component chain built for color. The component registry extends the Buttons template. A live Figma MCP feed keeps it current.

02

Agent – the system as context

Seven knowledge sources compile into one system prompt. Its guardrails turn “don’t hardcode a hex” and “Disabled is a state” into constraints the agent can’t reason around.

03

Execution – gated by approval

The agent proposes a plan first. Only once approved does it produce Figma frames, an HTML mockup and a spec together – a human stays the last check.
